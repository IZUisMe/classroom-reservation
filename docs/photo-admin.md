# 教室写真の管理（管理者PC専用）

## 起動と追加

1. [管理画面.cmd](<../管理画面.cmd>)をダブルクリックします。
2. **http://127.0.0.1:4174** をChromeで開きます。
3. 教室と写真の種類を選びます。
4. 写真を複数選択するか、選択エリアへドラッグ＆ドロップします。
5. プレビューを確認し、「追加」を押します。写真ごとに室内／外観を変更できます。
6. **「公開サイトへ反映」** を押し、確認画面で開始します。管理画面内に進捗と結果が表示されるので、公開完了まで待ってください。

公開ボタンは検査・ビルド・GitHubへの送信・公開完了待ち・画像と並び順の照合まで行います。CMDを開く必要はありません。公開中は追加・並び替え・削除をロックし、画面を再読み込みしても進捗を再取得します。失敗しても写真データはこのPCに残ります。

代わりに[写真を公開.cmd](<../写真を公開.cmd>)も利用できます。起動用CMDはPowerShellの **-NoExit** でエラーや結果が残る方式です。公開確認をキャンセルした場合も自動では閉じません。

停止は起動用ウィンドウで **Ctrl+C**。Windowsの起動用CMDは、この端末で動作確認済みのDeepSeek Harness付属Node.jsを優先し、存在しない場合はPATH上のNode.jsを使います。管理GUI自体には追加のnpm依存・ビルドは不要です。

## 既存写真の並べ替え・削除・復元

1. 教室を選ぶと、ROOMLIST等の既存資料写真と管理者が追加した写真を同じ一覧に表示します。写真を追加した後も、この一覧が自動更新されます。
2. PCでは写真カードをドラッグして並べ替えます。キーボードやタッチ操作では、カードの **←・→・↑・↓** ボタンを使えます。
3. 並べ替え・削除・復元は操作ごとにこのPCへ即保存し、**「保存済み・公開待ち」** と表示します。公開サイトへ反映するまでは一般利用者の表示は変わりません。
4. **「公開ギャラリーから削除」** は確認後に写真を非表示にします。確認画面は×・Esc・外側クリックでキャンセルでき、赤い「削除」を押したときだけ保存します。
5. 非表示の写真は **「削除済み」** を開き、**「公開ギャラリーへ復元」** で戻せます。画像ファイル・元資料・Git履歴は削除しないため、個人情報の完全削除を意味しません。

追加キューの **「一覧から外す」** は、その追加待ち一覧を整理する操作です。登録済みの写真や公開ギャラリーは削除しません。

別のタブで同じ教室が先に更新された場合は、最新一覧を読み込み、競合を表示します。古い並び順を自動で上書きせず、操作をもう一度行っていただきます。写真追加・一覧保存・公開中は同時編集を防ぐため操作ボタンを無効にします。

## 写真の制限

- 元画像：JPG・PNG・WebP。1枚20MBまで、一辺16384px以内・4000万画素以内。
- 一度の選択：30枚まで。変換・送信は1枚ずつ処理します。
- ブラウザ内で縦横比を保ち、拡大せず最大1440×1080の静止WebPへ変換します。
- ブラウザのCanvasを経由するため、元ファイル名・EXIF・位置情報・XMP等を保存しません。ファイル名は画面内の確認表示にのみ使用します。
- サーバーはWebPのみ受け付け、4MB／画像、本文6MB、RIFF/WEBP識別子・チャンク・寸法を検証します。メタデータやアニメーションのチャンクは拒否します。
- 追加失敗が表示された写真は、一度一覧から外してから選び直してください。追加済みの写真を再度選択すると、別写真として重複追加されます。

## どこに保存するか

管理用サーバーは**正本の公開用データ**を更新します。ビルド済みフォルダを直接書き換える方式ではありません。

- 管理写真台帳：`public/data/admin-photos.json`（schemaVersion 1）
- 写真：`public/images/rooms/admin-UUID.webp`
- 教室ギャラリー：`public/data/rooms.json`
- 写真出典台帳：`public/data/photo-sources.json`
- 並び順・削除設定：[写真編集台帳](<../public/data/photo-edits.json>)（教室ごとのorder／hidden）

写真の出典は「管理者追加」です。元資料に写真がなかった記録は履歴として残し、追加画像を独立したavailableレコードとして登録します。代表写真は、公開中の並び順で室内／外観それぞれの先頭写真です。削除は公開ギャラリーからの除外であり、画像URLやGitHub履歴からの完全消去ではありません。

データ再生成時も、管理写真台帳を統合する処理を通して管理写真を維持してください。再適用は冪等で、同じ台帳の読み込みによってギャラリーが重複することはありません。

## 安全性と公開範囲

- 管理者とは、この管理者PCにログインできる同一OSユーザーです。ログインフォームや共有の管理者パスワードは設けていません。
- 管理用サーバーは**127.0.0.1:4174にだけ待受**します。`HOST`や`PORT`環境変数は参照せず、LAN・インターネットへ公開しません。
- 公開GitHub Pagesには管理APIがありません。管理画面のHTML・JSも公開用ビルドには含めません。
- Host、更新リクエストのOrigin、起動ごとのランダムCSRFトークンを検証します。CORSを許可せず、追加・編集はPC内で処理します。「公開サイトへ反映」を確認したときだけGitHubへ送信します。
- ブラウザに配信するのは管理画面のHTML・JS・CSSと、出典台帳に登録されたWebPの確認画像です。任意のローカルファイルや回復記録を配信しません。
- GitHub認証はPCのGitHub CLI／キーチェーンを使い、ブラウザ・公開サイト・公開ソースへトークンを保存しません。
- 写真に人物や機密情報が写る場合の掲載可否は、管理者が追加前に確認してください。付加情報を除去しても、写真の画素に写った文字や顔は消えません。

## 更新の整合性

画像と4つのJSONの更新は、単一書込ロックと回復用記録を使って処理します。途中で書込に失敗した場合は元のJSONへ戻し、新しい画像も削除します。処理中にサーバーが終了した場合は、次の起動時に回復します。回復用記録は管理画面の作業用状態ディレクトリ内で、Web配信しません。

- 管理用サーバーで写真追加中に、別のデータ再生成処理を同時に実行しないでください。再生成する場合は先に管理用サーバーを停止してください。
- 回復に失敗したというエラーが出た場合は、書込権限・空き容量を確認し、管理用サーバーを再起動してください。回復用記録を削除すると元に戻せなくなるため、勝手に消さないでください。
- ロックが残った場合、元のプロセスが終了していれば次の起動で回収します。PIDが再利用される等で更新中と表示され続ける場合は、すべての管理用サーバーを停止してから管理者が状態を確認してください。

## 検証

[管理API・整合性テスト](<../tests/admin.test.mjs>)は、一時的な42教室fixtureを作成して検証し、本物の公開データを変更しません。

```text
node --test tests/admin.test.mjs
```

既存のPlaywright／Chromiumが利用できる開発環境では、GUIの変換・複数画像追加も実行できます。

```powershell
$env:RUN_ADMIN_BROWSER_TEST = '1'
node --test tests/admin.test.mjs
```

テスト用サーバーだけは空いているループバックポートを使用し、テスト終了時に停止します。通常の管理画面は4174固定です。
